# Table for One — decisions log

Last updated: **30 October 2026** (Asia/Kolkata).

This is the shared project memory for new Codex and Claude Code conversations. It explains the idea, why the current app looks the way it does, what is implemented, and what remains undecided. It supplements the code and product brief; it does not override the owner, `AGENTS.md`, or higher-priority instructions.

## Read this first

**The idea:** help people new to a city find belonging through a small shared meal. Table for One gets to know someone, understands their practical dining preferences, and invites them to a table of compatible people when a good fit exists. Food is the reason to meet; connection is the purpose.

**The intended product:** a Gurugram-first service for young professionals, with conversational onboarding, considered matching, trusted participants, restaurant reservations, and learning from post-meal feedback. It is not a dating app, networking event, social feed, or endless chat app.

**What exists today:** a working, responsive **browser-local demonstration** of the guest journey. It has guided onboarding, preferences, fictional sample tables, sample seat confirmations, simulated reflections, memories, and local privacy controls. It is **not** a live multi-user service. Guided questions are not live AI, fictional venue details are not real restaurant inventory, and local confirmation is not an actual booking.

**Where development should head:** review and improve the existing experience with the owner, then plan the operational, human-assisted pilot described in the PDF. Real backend/provider integrations are prerequisites for a live service. The owner has not yet chosen the next feature, backend, providers, or deployment target.

## Direction and open decisions

The following is the **agent's recommended sequence**, not an approved implementation backlog or permission to integrate/deploy services:

1. Open the existing project in Desktop, read this log and `AGENTS.md`, run the app locally, and collect the owner's feedback on the experience. Improve the existing implementation rather than rebuilding it without a reason.
2. Agree the next live-pilot milestone and acceptance criteria. The PDF's immediate roadmap is staff-run conversations and manual matching, not necessarily a fully automated AI launch.
3. Plan authenticated server persistence, authorization, consent, retention/deletion, and an operator workflow before accepting real personal data or bookings.
4. Select actual verification, venue/booking, payment/refund, notification, and safety-response arrangements. Providers, contracts, prices, deployment target, and production operating ownership remain undecided.
5. Add server-side AI onboarding/analysis and matching automation with evaluations and human fallback when the required product and operational foundations are in place. Never put provider secrets in `VITE_*` browser variables.
6. Measure real shared meals, show-up rates, table ratings, time to first table, safety/no-shows, and repeat bookings. The PDF proposes 40% repeat within 30 days as a hypothesis and a kill criterion below 30% repeat after eight pilot weeks; neither is an observed result or implemented analytics system.

Other unresolved details include the actual matching-quality threshold, identity/gender verification process, allergy handling at real venues, cancellation/refund/no-show policy, whether/how mutual eat-again choices become real repeat tables, and production accessibility/device validation. Existing sample behavior must not silently decide these product policies.
